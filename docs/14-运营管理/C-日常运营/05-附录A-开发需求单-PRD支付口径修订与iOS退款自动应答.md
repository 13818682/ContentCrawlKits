## 一、背景与目标

小程序已定稿采用**积分充值制**（PRD v2.2：充值档 ¥60/¥180/¥400/¥800，¥1 = 10 积分，积分消费解锁方案/学校完整版）。但现有 PRD 的**支付接入口径与微信平台规则冲突**，且**积分制 + iOS 虚拟支付的退款链路在现有设计中缺失**；另有**两项服务需按业务决定下线**（见 A6）。

**目标**：
1. 把 PRD 的支付口径从违规方案纠正为**小程序虚拟支付（Android 走微信支付 / iOS 走 Apple 支付）**；
2. 补齐 **iOS 退款问询自动应答**（3 秒 SLA）与**退款善后**能力；
3. 让**自建两池账本与微信托管代币账本可对账**，并把"在途收入"从可支配收入中剥离；
4. 补齐**合规文本入口与个人信息保护**——《用户协议》《隐私政策》《用户交易纠纷处理机制》三份文件已/即将成稿，**小程序内必须有可打开的页面**，否则"登录即表示同意"指向不存在的文件（见 B8、B9）。

## 二、需求明细

### A 类 · 文档修订（PRD 及配套）

#### A1【P0·合规】§7.6 支付接入口径改写

**现状（须改）**：
> "商户号类目 = 教育咨询；**iOS 充值走 H5 网页**（绕过苹果 IAP 30%，用户同价）"

**改为**：
> 支付接入 = **小程序虚拟支付**。Android / 鸿蒙 / Windows 端走微信支付，iOS 端走 Apple 支付（同一套代币/道具配置双端互通）。**不得引导用户至 H5、公众号、个人号、网站等站外渠道完成支付**（微信官方对虚拟商品的明文禁止项）。当前费率：Android 主动支付 1%（标准 10%），iOS 12%（标准 17%，全部为 Apple 佣金）。

**理由**：微信对虚拟商品强制要求接入小程序虚拟支付，且明令禁止引导至 H5 等站外渠道；2025-11 起 Apple 与微信已就小程序内购达成合作（iOS 佣金降至 12%），H5 绕行路径正是被该合作关闭的口子，继续执行将导致虚拟支付能力被关闭、小程序被限制或下架。

#### A2【P0】§1.3 退款条款增加 **iOS 分层表述**

现有"充值 = 预付款，未消费可退"在 iOS 端**无法由我方直接履行**（Apple 支付不支持开发者主动退款）。需补充分层：

> - Android / 鸿蒙 / Windows：由我方直接受理退款，原路退回，1–3 个工作日到账；
> - iOS：退款须由用户向 App Store 提出，结果由 Apple 决定；我方在收到退款问询时依据实际消费与交付情况提交处理建议，退款成立后收回相应积分与权益。

同步口径见 `04-附录A-用户交易纠纷处理机制` 第十七条。

#### A3【P0】§7.5 毛利表述修订：拆出**支付通道费**与**退款拨备**

现有"重用户全场景毛利 91.6%"是**服务成本口径，未扣支付通道费**。需改为：

| 层级 | 内容 |
|---|---|
| 毛利 | 服务成本口径（现有 91.6%，保留） |
| **− 支付通道费** | 新增独立行：Android 1% / iOS 12%（标准 17%）；按 iOS 占比估算综合费率 = 1% + 11% × iOS占比 |
| **− 退款拨备** | 新增独立行：建议按 iOS 充值流水 3%–5% 计提 |
| 净利 | 上述扣减后的结果 |

同时新增**收入确认口径**：iOS 收入区分「在途（已充值未结算，约 M+2～M+3）」与「已结算可支配」；回本测算按落袋月份计，不用充值发生月。

#### A4【P1】同步配套文档

`《计费模式对比（积分制VS综合制）》v2.12 → v2.17`：附录 G（支付接入）、附录 E（账务系统）按 A1–A3 同步修订；本文档与 PRD 冲突处以 PRD 新版本为准。

#### A5【P0】类目口径纠正（2026-09-13 据实际执照更新）

PRD 中"商户号类目 = 教育咨询"的表述作废。**小程序类目库中不存在"教育咨询"类目**；且本主体营业执照经营范围**不含"教育咨询服务"**，"课程销售"类目当前**不满足资质**。故改为：

> **主类目 = 工具 → 信息查询**（零资质，适用"提供信息查询、订单功能等服务"）；未来若付费形态做成课程/录播，可先线上增补经营范围"教育咨询服务"，再申请 **教育服务 → 课程销售**（需 ICP 备案核准 + 盖章版交易纠纷处理机制）。

**连带要求**：小程序内文案需与类目一致，**去除"课程、培训、授课、教学"字样**，定位为"数据查询 / 信息查询 / 方案参考"。

### B 类 · 功能实现

#### B1【P0】iOS 退款问询自动应答服务

**背景**：用户在 App Store 申请退款后，Apple 会向我方发起**最多 3 次**退款问询，**每次须在 3 秒内应答**，`evidence`（决策凭据）**必填**；3 次内均未应答，微信平台自动回"不确定"，决定权交 Apple。

**实现要求**：
1. 实现 `xpay_subscribe_ios_refund_query_notify` 推送的接收端点，**响应时延 < 3 秒**（含内部查询耗时）。
2. 依订单实际消费状态自动判定 `result_code`（决策矩阵见 `05-iOS端充值退款处理方案` §4.1）：
   - 未消费 → `0`（放过，建议退款）；
   - 部分/全额已消费且已交付 → `1`（拦截），附交付凭证；
   - 命中风控名单 → `1`，附风控记录。
3. **`evidence` 必填**且结构化（订单号、充值金额、积分发放、消费明细与时间、交付状态、协议条款引用），**不得为空或占位符**。
4. **幂等**：同一订单多次问询（最多 3 次）必须返回**一致**结论，不得因重复推送而改变判定。
5. **超时兜底**：内部查询超过 2 秒未返回时，按"最近一次已知状态"应答并**立即告警**（不得静默不应答）。
6. **全量留证**：每次问询的请求体、应答体、耗时写日志，保留不少于 3 年（对应纠纷机制第二十三条留档义务）。

#### B2【P0】代币账本 × 自建两池账本 一致性对账

**背景**：微信侧**托管代币余额**（`/xpay/query_user_balance`），PRD §1.3 的"现金池/赠送池"是**我方自建账本**；二者必须可对账，否则充值/消费/退款任一环节出错都无法定位。

**实现要求**：
1. 充值：现金充值 → 到账积分必须与微信侧代币余额增量一致；**赠送积分**通过代币赠送接口发放并单独记账。
2. 消费：`currency_pay` 扣减成功后同步落我方账本；失败/重试必须具备幂等键。
3. 消费退款：通过 `cancel_currency_pay` 逆操作，与自建账本同事务或可补偿。
4. 提供**日对账任务**：按日拉取微信侧账单（`/xpay/download_bill`、iOS 月账单 `/xpay/download_ios_settlement_bill`）与我方账本比对，输出差异清单。
5. 充值交易定性沿用 PRD：**"教育咨询服务费（预付款）"**，积分仅内部记账单位；账务上充值=合同负债，收入在服务交付时确认。

#### B3【P0】退款善后：积分回收 / 欠款积分 / 权益收回

收到 `xpay_refund_notify`（退款完成）后自动执行（明细见 `05-iOS端充值退款处理方案` §五）：
1. 扣回该笔对应积分，赠送积分一并回收；
2. 余额不足时形成"**欠款积分**"并记录；
3. 收回站内已解锁内容的访问权限；
4. 欠款未清期间**限制新的方案生成与解锁**（**已审批：历史已交付内容保留站内可查**，避免二次投诉与举证困难）；
5. 退款次数/设备指纹写入风险名单，同账号二次退款进入人工审核。

#### B4【P0】财务口径分栏

小程序侧需能导出：iOS **在途收入**（已充值未结算）与**已结算可支配收入**分列；通道费（Android 1% / iOS 12%）与退款拨备独立成栏。供运营侧 BP 与成本模型取数。

**⚠️ 前提：代码目前完全没有"支付渠道 / 手续费"概念**（已核实：`bff/src`、`miniapp` 中 `pay_channel` / `channel_fee` / `requestVirtualPayment` / `xpay` **零命中**；`recharge_orders` 只有 `amount_cny / points_cash / points_bonus / bonus_rule`）。**没有下列字段，B4 一条数都取不到**。需新增迁移：

```sql
-- recharge_orders 增列
pay_channel       VARCHAR(16)      -- 'wxpay' | 'apple'（下单时按设备分支落库）
channel_fee_rate  NUMERIC(6,4)     -- ★ 必须快照：0.0100 / 0.1200
channel_fee_cny   NUMERIC(10,2)    -- amount_cny × rate
net_amount_cny    NUMERIC(10,2)    -- amount_cny − fee（预计到账）
settlement_status VARCHAR(16)      -- 'in_transit' | 'settled'（iOS M+2~M+3）
settled_at        TIMESTAMPTZ

-- refund_orders 增列
source_order_id        UUID            -- 锚定原充值单（见 B10）
channel_fee_loss_cny   NUMERIC(10,2)   -- 本次退款渠道不退还的手续费（默认 0）
```

**★ 费率为什么要快照**：1% / 12% 是**优惠期价，标准为 10% / 17%**（见 04-微信侧 §4.2）。不落快照，费率一回调，历史对账永远不平、毛利口径漂移、退款损失算不准。

**口径定义（供实现与对账）**：

| 栏位 | 定义 |
|---|---|
| iOS 在途收入 | `pay_channel='apple' AND settlement_status='in_transit'` 的 `net_amount_cny` 合计——**不计入可支配现金** |
| iOS 已结算可支配 | `settlement_status='settled'` 的 `net_amount_cny` 合计 |
| 支付通道费 | `SUM(channel_fee_cny)`，按 `pay_channel` 分列 |
| 退款拨备 | iOS 充值流水 × **5%**（已审批，见 05-iOS §九） |
| 退款损失 | `SUM(refund_orders.channel_fee_loss_cny)`——**不得向用户转嫁**，计入平台期间费用 |

**`channel_fee_loss_cny` 计算口径**（与 05-iOS §七 待实测第 5、6 项联动）：

| 渠道 | 条件 | 损失 |
|---|---|---|
| wxpay | 支付 ≤180 天 | **0**（平台退还手续费） |
| wxpay | 支付 >180 天 | `rate × 退款额` |
| apple | 全部 | **0**（按净额追扣，佣金由 Apple 自担）——**待实测确认后固化** |

> **硬约束**：**绝不能从退款金额里扣手续费**。违反"未消费可退"承诺、违反平台规则、12315 风险；损失记为**平台期间费用**，不转嫁用户。

#### B9【P0】个人信息保护：隐私保护指引 + 未成年人单独同意

> ⚠️ **本节口径已修订（2026-09-13）**，见 `05-附录D-B9需求变更建议-个人信息保护口径重构.md`。
> 要点：① 《个人信息保护法》的未成年人分界线是 **14 周岁**而非 18 周岁，中考考生通常已满 14，第 31 条「监护人同意 + 专门处理规则」一般不适用；② §4.1 将「已满十四周岁未成年人信息」也定义为敏感个人信息，与第 28 条不符，需修订；③ **新增第 55 条「利用个人信息进行自动化决策须事前做影响评估」的硬义务**。以下正文保留原样以存变更痕迹。

**背景**：本服务处理的个人信息中含**未成年人信息**（考生姓名、就读初中、模考成绩），属《个人信息保护法》**敏感个人信息**，须取得**监护人同意**并作**单独告知**；小程序侧还强制要求 MP 后台配置**《用户隐私保护指引》**（未配置会导致 `getPhoneNumber` 等接口调用失败）。

**实现要求**：
1. **MP 后台配置《用户隐私保护指引》**，声明收集的信息类型与用途，与 05-附录C 口径一致。
2. 首次进入涉及个人信息填写的页面（考生档案）时**弹出隐私授权**，未同意不得采集；用户拒绝时提供可继续浏览的降级路径，不得静默失败。
3. **未成年人单独同意**：档案页对"考生信息"作单独告知，并提供监护人同意的勾选与留痕（与 05-附录B 第 7.3 条对齐）。
4. 提供**查阅 / 更正 / 删除 / 撤回授权**入口（可与账号注销流程合并，见 05-附录B 第 10.5 条）。
5. **采集范围最小必要**：现有 `user_behavior_logs` 记录 `ip / source_url / referrer / device_type`，`security_audit_logs` 记录 `device_fingerprint`，`blacklist_ips` / `rate_limit_records` 记录 IP 与频率——**须在 05-附录C 中逐项披露**，并确认每一项都有明确用途与留存期限（不能"先采了再说"）。

**验收**：
- [ ] MP 后台隐私保护指引已配置并通过校验
- [ ] 未同意隐私授权时，**不采集任何个人信息**
- [ ] 未成年人信息采集路径有**监护人同意留痕**
- [ ] 隐私政策披露的信息类型与实际采集**逐项对得上**（含 IP、设备信息、来源参数）

#### B10【P0】退款链路两个既有缺陷（配置商户号后即暴露）

**背景**：两条缺陷目前被 `NODE_ENV !== production` 的 mock 路径掩盖，**商户号一配上就暴露**，且都指向资金安全。见 §二 P2-2 与 `bff/src/routes/admin/refunds.ts`。

**缺陷 1 — 退款锚点选错单（会导致退款失败）**

`callWechatRefund` 生产路径取"该用户**最近一笔** `status='paid'` 的充值单"作退款锚点：

```sql
SELECT out_trade_no, amount_cny FROM recharge_orders
WHERE user_id = $1::uuid AND status = 'paid'
ORDER BY paid_at DESC NULLS LAST, created_at DESC LIMIT 1
```

若用户先充 ¥60、再充 ¥800（可退 ¥860），代码会拿**¥800 那张单**去退 ¥860，而微信 `amount.total` 为 ¥800 → **微信直接拒绝**（退款额不得超过单笔订单总额）。

> **要求**：改为按充值时间**正序 FIFO 逐单冲减**——一张单退不完就继续冲减下一张，逐单落退款记录。

**缺陷 2 — `recharge_orders.status` 的 `'refunded'` 从未被写入**

已核实：全仓只有 `point_orders` 会写 `refunded`，充值单不会写。退款成功后充值单**永远停留在 `paid`** → 上面的"最近一笔 `paid`"会把**已退过的单再选一次** → **重复退款风险**。`status` 枚举中已预留 `refunded`，只是无人写。

> **要求**：退款结算时同步把对应充值单置 `refunded`（或按 FIFO 的实际冲减金额置 `partial_refunded`），并加幂等守卫。

**验收**：
- [ ] 构造"先充 ¥60 再充 ¥800、退 ¥860"用例：**退款成功**，且两笔充值单状态正确
- [ ] 对同一退款单重复 `approve`：**第二次返回 409**，不产生第二笔微信退款
- [ ] 退款完成后的充值单**不再被选为退款锚点**
