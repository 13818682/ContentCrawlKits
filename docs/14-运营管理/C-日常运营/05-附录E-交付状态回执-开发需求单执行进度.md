### B1【P0】iOS 退款问询自动应答 —— **已完成**（2026-09-16，commit `c23cab4`）

| 交付 | 内容 |
|---|---|
| 端点 | `POST /v1/xpay/ios-refund-query`（**平台推送**，非小程序调用，故不走 JWT） |
| 决策矩阵 | 风控 → 未消费 → 部分消费 → 全额消费，五条分支 |
| 留证 | `ios_refund_queries`：请求体 / 应答体 / 耗时 / 结论，**逐次记录** |

**★ 首答即冻结**（本项最关键的实现选择）：需求单要求「同一订单 3 次问询必须返回**一致**结论」。
若每次按**当前**状态重算，用户在两次问询之间消费积分就会把结论从「放过」翻成「拦截」——**直接违约**。
故首次算出的结论落库，后续问询**原样重放**。

**但 `result_code` 为 NULL（查不到订单 / 超时）不冻结** —— 否则第一次的失败会永久锁死后续问询。
一句话：**返回了结论就冻结，没返回就不冻结。**

另有 **2 秒内部预算** + 兜底判定 + 告警（需求单第 5 条要求「不得静默不应答」）。

### B3【P0】退款善后 —— **已完成**（2026-09-16，commit `c23cab4`）

收到 `xpay_refund_notify` 后自动执行：扣回两池积分 → 余额不足形成欠款 → 风控归档 → 充值单置 `refunded`。

**四个已与经营者确认的决策**：

| # | 决策 | 理由 |
|---|---|---|
| 1 | **欠款只记现金口径**（不含赠送） | 赠送是营销成本、用户从未为它付钱；计入欠款会让用户「欠一笔他没付过的钱」。代价是平台自担该部分服务成本 |
| 2 | **充值冲抵时两池都参与** | 欠款是**积分欠款**，偿还时不挑池。若只允许现金抵扣，用户会反复充现金且每次赠送作废 |
| 3 | **允许部分抵扣递减** | 不允许递减 = 用户充了钱既不能消费、欠款也不减，**纯白花** |
| 4 | **权益侧不撤销** | 05-iOS §九 已审批「历史已交付内容保留站内可查」；代码内已注明，防后人「顺手补上」撤销逻辑 |

**★ 冲抵必须堵住的一个洗账漏洞**：`calcRefund` 的可退额按「累计充值 − 累计消费」推算。
若不把「用于冲抵欠款的金额」**单独记账并扣除**，用户即可
「充值 → 抵欠款 → 立即申请退款」，**把同一笔钱拿走两次，而欠款已清**。
实现上它记在 `total_debt_offset_cash`，**不能并进 `total_consumed_cash`** ——
后者是 B1 判定「这笔充值有没有被消费」的依据，混入抵债额会造成误判。

> **测试逮到的两个真 bug**（记此以免重犯）：
> ① `total_consumed_cash` 是**现金口径**计数器，与「现金＋赠送」总额比较属**单位混用**
> → 全额消费的订单被判成「部分消费 → 放过」→ **服务白送**。evidence 里的消费占比也必须同口径，
> 否则交给 Apple 的凭据会自相矛盾。
> ② 重放路径若不回填 `user_id` / `recharge_order_id`，留证**不可归属** ——
> 纠纷时无法回答「这次问询是哪个用户的哪笔单」，而留证正是 B1 第 6 条的目的。

B4 的 SQL 注释把 `pay_channel` 取值写为 `'wxpay' | 'apple'`。但**迁移前已存在的充值单没有渠道信息**，只能为 NULL；而经由小程序上报的订单也可能取不到设备平台（见 B5 兼容性）。

## 九、退款金额口径澄清：通道费不得转嫁，未消费退款不等于损失

> 本节回应执行中反复出现的两个判断：**① 能否从退款金额中扣除已发生的支付通道费；② 能否等平台把钱退回我方后再退给用户。**
> 二者均**不成立**。以下为结论、依据与处理意见，供运营侧据以统一对外口径。

### 9.1　结论

| 问题 | 结论 |
|---|---|
| 退款金额怎么算 | **= 用户实付金额中未消费的部分**，**不扣任何通道费** |
| 能否扣通道费 | **不能**。iOS 端**没有执行位置**；Android 端**没有法律依据** |
| 能否等平台退款后再退用户 | **iOS 端不适用**（我方不执行退款）；**Android 端不可行**（T+1 已结算，法律亦无宽限期） |
| 未消费退款的损失 | **0** —— 只是收入归零；服务未交付，即无成本 |

### 9.2　算例（iOS，用户未消费）

> 用户充值 ¥60 → Apple 即时扣 12%（¥7.2，我方应收净额 ¥52.8）→ 用户**未消费**。

**可退金额 = ¥60（全额），不是 ¥52.8。**

| 环节 | 金额 |
|---|---|
| 用户实付 | ¥60 |
| Apple 佣金（我方与 Apple 之间） | −¥7.2 |
| 我方应收净额 | ¥52.8 |
| **用户可申请退款** | **¥60** |
| **我方实际损失** | **¥0**（服务未交付） |

### 9.3　依据（由硬到软）

| # | 依据 |
|---|---|
| **1** | **合同相对性**：合同价款是 ¥60、用户**实付 ¥60**。Apple 的 ¥7.2 出在**我方与 Apple 之间**的结算里，不构成用户付款的组成部分，因而**不构成对用户的抗辩** |
| **2** | **法定可扣项只有一种，本场景不满足**：就网络购物退款而言，监管口径认可的例外是「消费者采用**信用卡**支付方式**并已支付**手续费」的，退款时可不退回该手续费（《网络购买商品七日无理由退货暂行办法》相关解读，见司法部「中国法律服务网」12348）。微信支付与 Apple IAP 的手续费均为**向商户收取**，用户实付金额中**没有独立的手续费项**，不适用 |
| **3** | **预付式消费新规直接写「返还本金」**：《最高人民法院关于审理预付式消费民事纠纷案件适用法律若干问题的解释》（2025-05-01 施行）第十四条——消费者有权自付款之日起七日内请求经营者**返还预付款本金**；已消费部分按约定单价抵扣，**赠送部分不予退还**（与 PRD 两池模型一致） |
| **4 ★** | **iOS 端物理上做不到**：我方**没有主动退款能力**（04-微信侧 §附录A 第十七条、05-iOS §一），Apple 判退即**全额退给用户 ¥60**，「扣 12%」这个动作**没有任何执行位置** |

> ⚠️ 第 2、3 项为法条适用判断，对外可见政策建议**由律师最终过一道**。但现口径是**对消费者更有利的一侧**，属风险较低的选择。

### 9.4　真损失在「已消费」，不在「未消费」

需求单与 05-iOS 目前未把这两件事分开讲，容易让运营侧**高估退款风险**，进而做出「扣通道费」这类得不偿失的应对。

| 情形 | 我方结果 |
|---|---|
| **未消费 + 退款** | 收入归零，**损失 = 0**（服务未交付，无成本） |
| **已消费 + 退款** | **服务白送，成本自担** ← **唯一的结构性真损失** |
| Android 退款 **≤180 天** | 平台退还手续费，**损失 0** |
| Android 退款 **>180 天** | 损失 = `rate × 退款额`（1%） |
| iOS 退款（Apple 若仅追扣净额） | **损失 0**；12% 是**每笔成功销售的恒定毛利折损**，非退款损失 |
| iOS 退款（Apple 若追扣含佣金） | 损失 12% —— **待实测**（05-iOS §七 第 5 项） |

**一句话**：「未消费的退款」不是损失，只是**没赚到**。「扣通道费」防的是一个**不存在的损失**，代价却是踩掉「未消费可退」的承诺——**12315 风险**，且《用户协议》第八条已对外承诺。

### 9.5　处理意见

| # | 意见 | 说明 |
|---|---|---|
| 1 | **维持现口径不动** |《用户协议》第八条与 05-附录A B4「硬约束」**均不需修改**；扣费口径一旦改动，是把**更严格的合规立场换成更松的**，收益（1%–12%）远小于风险 |
| 2 | **止血点在 B1/B3，不在退款扣费** | B1 决策矩阵把「已交付」拦下来（直接减少真损失）；B3 欠款积分负责拦截不成时的追回；风控名单压制高频「充值→退款」；5% 拨备做财务缓冲 |
| 3 | **建议采纳：不全额提现** | 不在微信虚拟支付账户全额提现，**留一部分余额作冲减缓冲**——这才真正解决「钱不在我方手上」的顾虑，而非向用户转嫁（05-iOS §六.2，原标「待实测」） |
| 4 | **替代目标** | 若确要降低退款率，应投向**产品侧**（提高交付感知、减少「充了没用」的存量余额），而非退款侧的扣费条款 |

### 9.6　与 05-iOS §七 待实测第 6 项的关系（建议改写该项）

原表述：

> 6. **部分退款**（用户已消费部分积分后退剩余）时，通道手续费**按比例退还**还是全额不退 —— 决定退款损失公式（需求单 B4 的 `refund_orders.channel_fee_loss_cny` 算法）

该句把**两个不同对象**混在了一起，容易被读成「可以从用户退款里扣手续费」：

| 对象 | 口径 |
|---|---|
| **对用户的退款额** | **不扣**，与本项无关（见 9.1–9.3） |
| **我方的期间费用**（才决定 `channel_fee_loss_cny`） | wxpay ≤180 天损失 0、>180 天损失 `rate × 退款额`；apple 按净额追扣、佣金自担（待实测） |

**建议**：第 6 项改写为分别陈述这两个对象，并明确「向用户扣减通道费**不在备选方案内**」。

> 本仓实现已按此口径落地：`bff/src/services/pay-channel.ts` 的 `refundFeeLoss()` 只计算**平台期间费用**，**绝不从退款额中扣减**（迁移 058 与集成测试已钉住该语义）。
