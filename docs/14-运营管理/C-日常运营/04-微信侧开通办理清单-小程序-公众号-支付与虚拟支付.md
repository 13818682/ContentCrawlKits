# 微信侧开通办理清单（积分充值制）

> **适用前提**：个体工商户已成立（2026-09，**深圳市罗湖区旭日领航信息咨询工作室**）、工行对公账户已开、小程序设计完成度 ~90%。经营范围含"信息技术咨询服务 / 信息咨询服务（不含许可类信息咨询服务）/ 互联网数据服务 / 大数据服务 / 软件开发 / 人工智能应用软件开发 / 社会经济咨询服务 / 互联网销售"等，**许可经营项目：无**；⚠️ **不含"教育咨询服务"**——直接影响类目选择，见 §3.4。
> **计费口径**：小程序采用**积分充值制**（充值 → 到账积分 → 用积分解锁方案/学校完整版），充值档 ¥60 / ¥180 / ¥400 / ¥800，¥1 = 10 积分（PRD v2.2；**预置专题与专家核验深度咨询两项服务已于 2026-09-13 取消**）。
> **口径声明**：金额与费率均为 2026-09 官方文档口径；标注「⚠️ 以实付页为准」的项目属平台优惠价，可能随时回调。

## 一、结论速览（先看这 7 条）

1. **必须办的还是 4 件事**：小程序注册 → 小程序认证 → 小程序备案 → 开通小程序虚拟支付；类目设置是这 4 步之间的必过闸口。
2. **积分充值 = 虚拟支付里的「代币充值」形态，只能走小程序虚拟支付**。PRD v2.1 §7.6 写的"**iOS 充值走 H5 网页**（绕过苹果 IAP）"是**微信明令禁止**的做法（官方原文：虚拟商品"购买和支付均需接入小程序虚拟支付；**不得引导至 app、公众号、H5、个人号、网站完成支付**"）。**该方案必须作废**，iOS 端改走小程序虚拟支付自带的 Apple 支付通道——这也是 2025-11 起微信已正式开放的合规通路。风险与替代见 §3.5、§七.1。
3. **年费仍然很低**：小程序认证 **¥30/年**（个体户优惠价，标准 ¥300）；备案 **免费**；虚拟支付开通 **免费**。公众号认证 ¥300/年可暂缓。
4. **抽成发生在「充值」这一步，消费积分时不再抽成**：Android/鸿蒙/Windows 端 **1%**（标准 10%）；iOS 端 **12%**（全部为 Apple 佣金，标准 17%）。
5. **iOS 的 12% 不是用户额外多交钱**，而是从用户实付的充值款里**先扣 12%**，余额由 Apple 结算给我方（到账周期长，见 §4.4 与 §4.5）。
6. **代币（积分）一经发布，名称与兑换比例不可修改**——"¥1 = 10 积分"必须在上线前定死；消费侧按城市/按产品的积分价不受影响，仍可在后台随时配置。
7. **时间上最不可控的仍是备案**：通管局 **1–20 个工作日**，未备案不能上线。设计已到 90%，备案应当今天就启动。

## 二、办理依赖关系与顺序（照这个顺序走，不要跳）

```
①小程序注册 ─→ ②微信认证 ─→ ③小程序备案 ─→ ④服务类目设置 ─→ ⑤虚拟支付开通 ─→ ⑥代币(积分)配置
（个体户，免费）（¥30/年）   （免费，1–20工作日）（工具-信息查询）（免费，1–7工作日）（比例不可改，慎）
                                                                                        │
                              （如需内容承接/服务号能力）⑦ 公众号 + 认证 ¥300/年 ────────┘ 并行，不阻塞
```

**关键路径 = ③备案**；④⑤⑥可在备案审核期间并行准备材料，但⑤要求小程序**已认证**（②完成即可）。

### 3.4 小程序服务类目设置 ★ 决定"能不能卖"和"能不能开虚拟支付"

> ⚠️ **2026-09-12 校正（据实际营业执照）**：本主体全称 **深圳市罗湖区旭日领航信息咨询工作室（个体工商户）**，经营范围中**没有"教育咨询服务"**（现有为：大数据服务、互联网数据服务、软件开发、人工智能应用软件开发、信息技术咨询服务、信息咨询服务（不含许可类信息咨询服务）、社会经济咨询服务、市场营销策划、项目策划与公关服务、专业设计服务、数字文化创意软件开发、互联网销售等；许可经营项目：无）。
> 因此**此前设想的「教育服务-课程销售」路径当前不可行**——该类目硬性要求《营业执照》经营范围含"教育咨询服务"。方案已改为主推「**工具-信息查询**」。

**结论：主类目选「工具 → 信息查询」——零资质、不改执照、最快过审。**

| 类目 | 资质要求 | 类目适用范围（官方原文） | 判断 |
|---|---|---|---|
| **工具 → 信息查询**（主推） | **无** | "适用于提供信息查询、订单功能等服务" | ✅ 本小程序核心功能 = 分数/学校/政策**数据查询** + 方案信息呈现，落在释义内；执照含"信息咨询服务、信息技术咨询服务、互联网数据服务、大数据服务"，与类目口径、备案口径三者一致 |
| 工具 → 预约/报名 | 无 | "适用于提供预约/报名功能等服务" | ⚪ 可选补充（若开放预约类功能） |
| 教育服务 → 课程销售 | ① ICP 备案核准或增值电信业务经营许可证 ② **执照经营范围需含"教育咨询服务"** ③ 盖章版交易纠纷处理机制 | "适用于提供线上课程销售等服务" | ❌ **当前不符**（执照无"教育咨询服务"）；且我方卖的是方案/数据查询，不是课程 |
| 教育服务 → 学历教育 / 非学科类培训机构 / 成人技能培训 / 在线视频课程 / 出国留学 | 需《民办学校办学许可证》《非学科类校外培训机构培训许可证》等 | — | ❌ 个体户办不下来；且会触发"培训"前置许可，直接越线 |
| 商业服务 → 咨询 | — | — | ❌ 小程序类目库**无"咨询"子类目**（该一级下仅：律师、企业管理、会展服务、公关/推广/市场调查、环保回收、摄影/扩印） |

**为什么不能归"教育类"**：教育服务一级类目下当前**已无**「教育信息服务」「在线教育」子类目；与教育相关的可选子类目全部要求办学许可证或课程销售资质。"考试分数/学校信息查询"类服务在微信生态里由「工具-信息查询」承载。

#### ⚠️ 一处必须分层表达的口径：业务定位 ≠ 平台类目

| 场合 | 怎么说 | 为什么 |
|---|---|---|
| **业务定位**（《用户协议》《用户交易纠纷处理机制》、客服话术、对外介绍） | 本服务是 **"中考志愿填报咨询服务"** | 这是业务实质，也与执照经营范围里的"**信息咨询服务**"对应，表述成立 |
| **平台类目**（对微信，MP 后台） | 必须选 **「工具-信息查询」** | 微信类目库**没有"咨询"类目**；教育类目要么要办学许可证、要么要执照含"教育咨询服务"，两者都不满足 |
| **小程序内的功能命名与页面文案** | 落"**查询 / 数据 / 方案参考**"（如"学校查询""分数查询""方案参考"） | 类目审核要求"类目与实际服务一致、且用户在该页面能直接使用该服务"；类目对应页面里出现"咨询服务"字样会增加被判"类目不符"的风险 |

**执行规则**：**协议与对外业务表述用"咨询服务"，平台类目与小程序内页面呈现用"信息查询"**——两者不矛盾，但不要写串。

**运营侧必须配合的三条**：

1. **小程序内文案口径要与类目一致**：对外定位为"数据查询 / 信息查询 / 方案参考"，**避免出现"课程、培训、授课、教学"字样**。审核规则明确：类目必须与所提供服务一致，且用户在该页面能直接使用该服务（不得隐藏、不得多次跳转）。文案口径不符是"类目与服务不符"驳回的主因。
2. **备案环节的"服务内容"要与类目对齐**：小程序备案时选"工具"类（该指引写明"单位备案：可选，需符合单位经营范围"），我方执照的信息技术/信息咨询类经营范围与之匹配。
3. **类目位是有限资源**：一个小程序最多 **5 个服务类目**，每月 **5 次**修改机会。建议**给未来的「教育服务-课程销售」留一个位子**——若日后付费形态真的做成"课程/录播"，再线上增补经营范围「教育咨询服务」（深圳可线上变更，通常免费、数个工作日）后申请该类目。

**要不要现在就增补经营范围？建议暂不。** ① 现有路径不需要它；②「课程销售」释义是"线上课程销售"，我方业务不是课程；③ 增补后仍需 ICP 备案核准（已有）+ 盖章纠纷机制（已备），不带来新增能力。**等业务形态真需要课程类目时再补。**

**发票名目相应调整**：见 §4.6——**不要再写"教育咨询服务费"**。

### 3.5 小程序虚拟支付开通 ★ 积分充值制的主通道

| 项 | 内容 |
|---|---|
| 开通条件 | ① 小程序**已认证** ② 主体为**企业/事业单位/个体工商户** ③ 主体信息完备 |
| 入口 | MP 后台左侧栏 → **虚拟支付** |
| 流程 | ① 同意虚拟支付协议 → ② 提交商户资料（营业执照、**提现账户**、支付管理员信息）→ ③ 审核（**1–7 个工作日**）→ ④ 账户验证（**支付管理员填经营者本人则跳过**）→ ⑤ 扫码签约 → ⑥ 约 1–2 个工作日后再进，显示「已签约」即商户号开通成功 |
| 费用 | **开通免费**，按笔收技术服务费（见 §四） |
| 后台能力 | 基础配置（appid/offerid/appkey、发货订阅）、**代币配置**、**道具管理**、资金管理（余额/提现/日账单）、交易订单（含退款）、广告金 |

#### 3.5.1 积分制（代币充值）对接要点 ★ 与 PRD 的账务模型必须对齐

| # | 要点 | 对我方的影响 |
|---|---|---|
| 1 | **代币名称与兑换比例一旦发布不可修改** | "¥1 = 10 积分"必须上线前定死；改动只能新建代币并处理存量积分 |
| 2 | 平台提供**代币充值 → 代币扣减 → 代币退款 → 代币赠送**四类接口 | PRD 的"充值赠送积分"对应 `present_currency`；"消费扣积分"对应 `currency_pay`；"消费退款"对应 `cancel_currency_pay` |
| 3 | **代币余额由微信侧托管可查**（`query_user_balance`） | PRD §1.3 的"现金池/赠送池两池模型"是**我方自建账本**，必须与微信侧代币余额保持一致性对账；两池的拆分只能在我方系统内实现 |
| 4 | **配置的道具/代币 Android、iOS 双端互通** | 一次配置双端可用，iOS 端不需要另建一套商品 |
| 5 | 代币充值属"**主动支付**"场景 | 适用 §4.2 的主动支付费率（1% / 12%），**不适用**"会员订阅（自动续费）第二笔起 10%"那条 |
| 6 | 消费侧积分价（方案 600 / 学校 50）**由我方后台控制** | PRD §六「每个城市每产品积分价独立配置」的弹性**仍然成立**，不受代币比例锁死影响 |
| 7 | 用户充值所得的代币**不可提现、不可兑换现金、不可转让** | 需写入用户协议（也是监管对虚拟货币的要求） |
| 8 | 退款：现金单经 `refund_order` 原路退回；支付 **180 天内**平台退还手续费，超期不退 | 与 PRD 的"未消费可退"一致，但 **iOS 端不适用**（见 §4.4） |

**iOS 端额外条件（不满足则 iOS 用户看不到充值入口）**：

- 已开通小程序虚拟支付
- 必须在 MP 后台**配置小程序简称**（Apple 支付展示 display name 需要）
- 用户侧：iPhone/iPad 且 **iOS 15+**、微信 **8.0.68+**、**单笔最低 ¥1**、**仅中国大陆 App Store 账户**
- **Apple 支付不支持沙箱环境**，只能现网联调（建议用 ¥1 商品真机测）

**红线**：虚拟商品**不得引导至 app / 公众号 / H5 / 个人号 / 网站完成支付**；若小程序仅含虚拟类目，平台会**关闭该小程序在安卓及其余非 iOS 系统的普通微信支付能力**。

### 3.6 微信支付普通商户号：本项目**不需要单独申请**

充值走虚拟支付，开通时平台会自动开一个新的微信支付商户号用于结算提现。只有出现**实物商品 / 线下服务 / 公众号内收单**时才需要另申请普通商户号（申请免费，费率 0.6%–1%，教育类 0.6%，结算 T+1，个体户可绑对公或法人对私账户）。

### 3.7 微信公众号

不是变现前置，**不阻塞充值上线**。个体户可注册**服务号**（个人主体只能订阅号、不能微信支付）；认证 **¥300/年**，与小程序认证**分开收费、独立年审**。建议**等到需要"公众号内收单/模板消息触达"时再升级+认证**。

### 3.9 小程序隐私合规：隐私保护指引 + 隐私政策 ★

**背景**：本项目处理的个人信息中含**考生信息**（姓名/称呼、就读初中、模考成绩等），**可能涉及未成年人**；微信侧有强制配置项，《个人信息保护法》另有两项硬义务。**注意：未成年人分界线是 14 周岁、不是 18 周岁**（见 §3.9.1）。

**两件事，缺一不可**：

| 项 | 位置 | 说明 |
|---|---|---|
| **《用户隐私保护指引》** | **MP 后台**（设置 → 服务内容声明 → 用户隐私保护指引） | 微信**强制**。未配置或与实际采集不符，会导致 `getPhoneNumber`、`chooseImage` 等接口**调用失败**——不是警告，是接口直接不可用 |
| **《隐私政策》** | 小程序内页面 | 对外公示的个人信息处理规则，成稿见 `05-附录C`；与《用户协议》第十条互为引用 |

**必须逐项披露的采集项**（已核实代码与库表，**不能只写常规项**）：

| 类别 | 具体项 | 来源 |
|---|---|---|
| 账号信息 | `openid` / `unionid` / 昵称 / 头像 | 微信授权登录 |
| 联系方式 | 手机号（**可选**绑定，运营回访用，脱敏展示） | `wx.getPhoneNumber` |
| **考生信息**（可能涉及未成年人） | 考生姓名（建议只填"称呼"）、户籍类型、就读初中、年级排名、模考成绩、意向学校 | 用户填写 |
| 设备与日志 | **IP 地址**、设备类型、来源参数（`source` / `source_url` / `referrer`） | `user_behavior_logs` |
| 安全风控 | **设备指纹**、风险评分、风控标记 | `security_audit_logs` |
| 交易 | 充值订单号、金额、微信交易号、积分流水 | `recharge_orders` / `point_transactions` |

**红线**：① 采集范围须**最小必要**，不得"先采了再说"；② 隐私政策与 MP 后台指引披露的信息类型必须与实际采集**逐项对得上**——这是审核与投诉时最容易被挑的点；③ **不满十四周岁**考生须先取得监护人同意（已满十四周岁的按一般个人信息处理，填写者出具授权声明即可）；④ **禁止**在政策或客服话术中出现"未收集个人信息"这类不实表述（见 §3.9.1）。

#### 3.9.1 三个容易搞错的口径（2026-09-13 据 `05-附录D` 校正）

| # | 口径 | 正确说法 |
|---|---|---|
| 1 | **分界线是 14 周岁，不是 18 周岁** | 《个保法》**第 31 条**只对**不满十四周岁**的未成年人要求"监护人同意 + 专门个人信息处理规则"；**第 28 条**也只把**不满十四周岁**未成年人的个人信息列为敏感个人信息。中考考生通常已满 14 周岁，**不触发**第 31 条。原"未成年人信息一律属敏感个人信息、一律要监护人同意"的表述**与法条不符**，会让本服务自愿承担不必要的高义务 |
| 2 | **去标识化 ≠ 不是个人信息** | 去标识化后的信息**仍是个人信息**（第 73 条），仍受《个保法》约束。**不得**在政策或对外话术里写"未收集/未获取个人信息"——那违反**第 17 条**的真实、准确、完整告知义务，等于自己制造一个新的违法点。准确表述是"**最小化采集 + 不采集敏感个人信息**" |
| 3 | **自动化决策是躲不掉的硬义务** | 本服务核心功能（模拟推算 + 生成志愿方案）构成**第 73 条**意义上的"**自动化决策**"，依 **第 55 条**须**事前进行个人信息保护影响评估（PIA），并保存记录至少三年**（第 56 条）。此项**与是否脱敏、是否涉及未成年人无关**，由服务形态决定。PIA 由 `1.HSEE-Prj` 起草、运营侧会签 |

**微信隐私接口实测结论**（1.HSEE-Prj 已核实）：自有代码调用的微信隐私接口**只有手机号一项**；填写考生档案**不调用任何微信隐私接口**，微信框架**不会**自动触发隐私弹窗——考生信息的告知义务由《隐私政策》正文承担，不必为此建独立弹窗。

### 4.4 ★ iOS 端那 12% 到底怎么扣（回答提问）

**问**：iOS 用户在小程序里充值，是不是要"自动交纳 12% 给苹果公司"？

**答：是扣，不是交；而且不是用户额外多付 12%，是从用户付的那笔钱里先扣 12%。**

用户在 iOS 微信小程序内点充值后的完整链路：

```
用户点充值 ¥60
   ↓
① 小程序虚拟支付按设备路由 → iOS 端拉起【Apple 支付】（不是微信支付）
   ↓
② 用户按标价支付 ¥60（Apple 不向用户另加价，用户看到的就是 ¥60）
   ↓
③ ¥60 先进入 Apple 的结算体系，Apple 扣除 12% 佣金 = ¥7.2
   ↓
④ Apple 在【自然月结束后 45–60 天】把 ¥52.8 汇给腾讯
   ↓
⑤ 腾讯收到后划转到我方虚拟支付账户 → 到账后可提现到对公账户
```

**四个必须记住的结论**：

1. **扣在源头，不落在用户头上**：用户实付 = 标价；我方到手 = 标价 × 88%。用户不会看到"额外 12%"的收费项。
2. **开发者侧没有"缴费"动作**：不需要申报、不需要转账，是 Apple 在结算环节自动扣减，我方只在账单里看到净额。
3. **钱先到 Apple 手上，到账慢 2–3 个月**：iOS 充值的现金流入要按 **M+2～M+3** 计入，做回本测算时不能当"当月收入"。
4. **12% 是"当前生效费率"，标准是 17%**（含 12% Apple 佣金 + 5% 微信技术服务费）。优惠期结束，iOS 端会从 12% 变 17%，**定价模型必须为这个回调留缓冲**。

**为什么不能"iOS 走 H5 网页绕过"**：微信官方规则原文把"H5"列为**禁止引导的支付渠道**；且 2025-11 Apple 与微信已就"小程序内购"达成合作（把 iOS 佣金从常规 30% 降到 12%～15%），**H5 绕行这条路正是被这次合作收编关闭的**。此时走 H5，代价是小程序虚拟支付能力被关闭、小程序被限制或下架，收益只有省下 12 个百分点——**风险收益完全不成立**，只能按 §4.5 从定价侧消化。

## 六、风险与避坑

1. **【最高优先级】不要走 H5 绕行**。微信明文禁止引导站外/H5 支付，且这正是 2025-11 苹果与微信小程序内购合作要关闭的口子。后果是虚拟支付能力被关闭、小程序被限制或下架。
2. **iOS 端我方"不能主动退款"**（详见附录A 第十七条）：Apple 支付下，退款申请由用户在 App Store 提出，我方只能应答 Apple 的退款问询。**PRD §1.3"充值未消费可退"的承诺在 iOS 端无法由我方直接履行**，必须在用户协议里做分层表述，否则构成虚假承诺。
3. **代币比例不可逆**："¥1 = 10 积分"发布后不可修改。虽然消费侧积分价仍可自由配置（PRD §六的弹性保留），但兑换比例的容错为零——上线前必须评审签字。
4. **类目口径**："教育咨询"不是小程序可选类目；**主类目已定「工具-信息查询」**（执照无"教育咨询服务"，「课程销售」不满足资质，见 §3.4）。
5. **备案是唯一长尾**：通管局 1–20 工作日、退回即重排；执照地址/负责人手机号必须与工商登记一致。
6. **iOS 账期 + 无沙箱**：现金流入按 M+2～M+3 计；iOS 支付联调只能用真机真单。
7. **年审别忘**：小程序认证到期前 3 个月平台提醒，逾期认证状态失效 → 虚拟支付一并受影响。把年审日写进运营日历。
8. **主体变更会打断支付**：将来"个转企"时虚拟支付商户号需以公司主体重开（审核 5–7 工作日 + 回调重配 + 代币需重新配置），预计 **1–2 周支付中断**；按 A/01 结论安排在 **9–12 月淡季**，变更前个体户保持存续不注销。
9. **费率是优惠价不是承诺**：Android 1%（标准 10%）、iOS 12%（标准 17%）。**不要把 1% 写进长期成本模型**。
